# Архитектура базы данных приложения (GUI для врача)

Реализация: `gui/database.py` (SQLite, только стандартная библиотека + numpy/opencv,
которые уже есть в проекте). Самопроверка: `python gui/database.py`.

## Почему SQLite, а не серверная СУБД

Приложение — настольное, один врач за одной рабочей станцией. SQLite:

* не требует установки и администрирования СУБД в клинике (важно для ИТ-отдела больницы);
* вся база — один файл `nir.db`, бэкап = копирование файла (при закрытом приложении);
* режим WAL защищает от повреждения при внезапном отключении питания.

Каталог данных: `%APPDATA%/NirSeg/` (Windows) или `~/.local/share/NirSeg/` (Linux).
Внутри: `nir.db` + `data/study_<id>/...` — файлы изображений, масок, оверлеев.

Ключевой принцип: **в БД — только метаданные и относительные пути**; бинарные
файлы лежат рядом в `data/`. База остаётся маленькой и быстрой, а пара
«nir.db + data/» переносится на другую машину целиком.

## Схема

```
users (врачи/админы)
  │
patients (пациенты: номер карты, ФИО, дата рождения, пол)
  │ 1:N
studies (исследования: дата, локализация, клинический диагноз, лечащий врач)
  │ 1:N
slides (препараты: имя файла, окраска H&E, MPP)
  │ 1:N
images (изображения/фрагменты: путь, размеры, SHA-256)
  │ 1:N
predictions (маска, оверлей, режим single/ensemble, TTA,         ← models (реестр
             доли классов в JSON, время инференса, кто запустил)    версий моделей)
  │ 1:N
corrections (правки врача: исправленная маска + комментарий; оригинал не затирается)

reports (заключения по исследованию: файл + автор)   ← ссылка на studies
audit_log (кто / что / когда / детали — на любое изменение данных)
```

Назначение ключевых решений:

| Решение | Зачем |
|---|---|
| `predictions.model_id → models` | Каждое заключение воспроизводимо: известно, какая версия весов использовалась. Обязательное требование к медицинскому ПО. |
| `models (name, version) UNIQUE` | Нельзя «тихо» подменить чекпоинт; новая версия весов = новая запись. |
| `class_areas` JSON | Доли тканей (tumor/stroma/lymphocytic/necrosis/fat, %) считаются один раз при сохранении — сводка и заключение строятся без перечитывания масок. |
| `corrections` отдельной таблицей | Правка врача никогда не перезаписывает машинную маску — это и история, и готовые данные для дообучения. |
| `audit_log` | Прозрачность: любой(create/update/delete/export) факт зафиксирован. Защита при разборе спорных случаев. |
| `images.sha256` | Дедупликация и контроль целостности: файл не «протух» и не подменён. |
| `get_study_summary` берёт **последнее** предсказание каждого изображения | Сводка для заключения не искажается историей повторных прогонов. |
| `PRAGMA user_version` + миграции | Обновление приложения не ломает существующие базы врачей. |

## Рабочий процесс врача в приложении

1. Найти/создать пациента (поиск по номеру карты или фамилии — `find_patient`).
2. Создать исследование (дата, локализация, клинический диагноз).
3. Добавить препарат и импортировать изображение (`import_image` — файл копируется
   в каталог данных, приложение больше не зависит от исходного пути).
4. Запустить сегментацию (одна модель или ансамбль, с/без TTA) — результат
   сохраняется через `save_prediction` вместе с долями классов.
5. При необходимости поправить маску — правка уходит в `corrections` с комментарием.
6. Сформировать заключение: `get_study_summary` даёт средние доли тканей по
   исследованию; рендер отчёта (HTML/PDF) пишется в `reports`.

## Интеграция в GUI (что менять в mainwindow.py)

* После `on_prediction_finished` вызвать `save_prediction(...)` — маска уже есть
  в `self.current_mask`, оверлей в наличии.
* Добавить экран «Пациенты/Исследования» (QTableView + QSortFilterProxyModel над
  `list_studies`) и диалог «Новое исследование» перед анализом.
* «Сохранить маску» переделать с «сохранить в любую папку» на сохранение в БД;
  свободное сохранение оставить как «Экспорт» с записью в audit_log.

## Замечания для реального клинического использования

* **Персональные данные**: `patients` содержит ФИО и номер карты. Минимум —
  ограничить доступ к каталогу `%APPDATA%/NirSeg` учёткой врача; при передаче
  базы в исследование — экспорт без таблицы patients (обезличивание одной
  таблицей). При необходимости — SQLCipher (шифрование файла БД целиком).
* **Пароли**: сейчас `password_hash` — поле под готовый хэш (например,
  `pbkdf2_hmac` из hashlib). Хранить пароли открытым текстом нельзя.
* **Бэкапы**: простой план — при выходе из приложения копировать `nir.db`
  в `backups/nir_ГГГГММДД.db`, хранить последние N копий (2–3 строки кода).
* **ONNX**: когда GUI перейдёт на onnxruntime, в `models.ckpt_path` пишется путь
  к .onnx; схема не меняется.
